## Where things live

The game rules live in `core/`. `session.gd` manages food, growth, score, collisions, and game states. `dragon.gd` handles movement and direction changes, while `board.gd` defines tile kinds and solid cells.

The presentation layer lives in `app/`. `main.gd` receives player input, passes directions to the session, and updates the snake, food, camera, and UI based on the game state. `stage.gd` loads the meshes and draws the arena.

The 3D assets are generated by `tools/build_art.py` and exported to `art/dragon_kit.glb`. The tests in `tests/` verify the game rules independently of the presentation layer.

## Adding a tile kind

1. Add a new tile kind to `Board.TILES` in `core/board.gd` and define whether it is solid.
2. Create a builder function for the new tile in `tools/build_art.py`.
3. Register the builder in `TILES` using the same tile name.
4. Update the board generation to include the new tile.
5. Run `deno task art` to regenerate the 3D assets.
6. Run `deno task kit` and `deno task ci` to check the assets and game rules.

## Patterns, and what they bought us

- **Command:** The turn queue in `core/dragon.gd` stores direction changes and applies them on successive ticks. This allows the game to handle quick player inputs without losing them.

- **Type Object:** `Board.TILES` defines different tile kinds and their properties. New tile kinds with existing behaviors can be added without changing the collision logic, following the Open/Closed Principle.

- **Flyweight:** The snake segments share meshes in `app/main.gd`. This reduces repeated mesh data.

- **Single Responsibility Principle:** The core handles game rules, while the presentation layer handles input and rendering. This makes the code easier to maintain and allows us to test the rules independently.

## One idea we carried over

- **The problem:** When game rules are mixed with rendering and input handling, it becomes difficult to test the game or change its presentation without affecting gameplay.

- **The practice:** Similar to our previous TypeScript projects, we separate the game rules from the presentation layer. The presentation layer sends player actions to the core and reads its updated state.

- **The mechanism:** In Godot, we use GDScript classes extending `RefCounted` for the game rules and `Node3D` for the presentation layer. Compared to TypeScript, Godot provides built-in tools for rendering, input, and scene management. However, we still need to maintain a clear boundary between the rules and the engine.
